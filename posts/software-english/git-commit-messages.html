Git Commit Message 작성 가이드

소프트웨어영어 · 2025.10.29

좋은 커밋 메시지의 중요성

Git 커밋 메시지는 프로젝트의 히스토리를 기록하는 중요한 문서입니다. 명확하고 일관된 커밋 메시지는 팀 협업과 코드 리뷰를 원활하게 만들며, 나중에 코드 변경 사항을 추적할 때 매우 유용합니다.

기본 구조

<type>: <subject>

<body>

<footer>

1. Type (타입)

커밋의 종류를 나타냅니다.

  • feat: 새로운 기능 추가 (A new feature)
  • fix: 버그 수정 (A bug fix)
  • docs: 문서 변경 (Documentation only changes)
  • style: 코드 포맷팅, 세미콜론 누락 등 (Formatting, missing semi colons, etc)
  • refactor: 코드 리팩토링 (Code change that neither fixes a bug nor adds a feature)
  • test: 테스트 코드 추가/수정 (Adding or updating tests)
  • chore: 빌드 프로세스, 도구 설정 등 (Updating build tasks, package manager configs, etc)
  • perf: 성능 개선 (Performance improvements)

2. Subject (제목)

변경 사항을 간결하게 요약합니다.

규칙:

  • 50자 이내로 작성
  • 첫 글자는 대문자로
  • 명령형(imperative mood) 사용
  • 마침표 사용하지 않음

좋은 예:

Add user authentication feature
Fix login validation bug
Update README installation guide

나쁜 예:

added user authentication feature.  (과거형, 마침표)
fix bug  (너무 모호함)
Updated the README file with new installation instructions that are more detailed  (너무 김)

3. Body (본문) - 선택사항

상세한 변경 사항을 설명합니다.

  • 무엇을, 왜 변경했는지 설명 (What and Why, not How)
  • 72자마다 줄바꿈
  • 제목과 본문 사이 빈 줄 추가

4. Footer (푸터) - 선택사항

이슈 트래커 ID, Breaking Changes 등을 명시합니다.

Closes #123
Fixes #456
BREAKING CHANGE: API endpoint /api/v1/users changed to /api/v2/users

자주 사용되는 동사

추가 (Adding)

  • Add - ~을 추가하다
  • Introduce - ~을 도입하다
  • Implement - ~을 구현하다
  • Create - ~을 생성하다
Add email validation to registration form
Implement password reset functionality
Create user profile page

수정 (Fixing)

  • Fix - ~을 수정하다
  • Correct - ~을 바로잡다
  • Resolve - ~을 해결하다
  • Patch - ~을 패치하다
Fix memory leak in data processing
Correct typo in error message
Resolve CORS issue on API endpoints

변경 (Changing)

  • Update - ~을 업데이트하다
  • Modify - ~을 수정하다
  • Change - ~을 변경하다
  • Refactor - ~을 리팩토링하다
  • Improve - ~을 개선하다
Update dependencies to latest versions
Refactor authentication middleware
Improve database query performance

제거 (Removing)

  • Remove - ~을 제거하다
  • Delete - ~을 삭제하다
  • Drop - ~을 제거하다
Remove deprecated API endpoints
Delete unused CSS files
Drop support for IE11

완전한 커밋 메시지 예제

예제 1: 간단한 커밋

feat: Add dark mode toggle button

예제 2: 본문이 있는 커밋

fix: Prevent race condition in user registration

The registration process could fail when multiple requests
were made simultaneously. Added mutex lock to ensure thread
safety during user creation.

Fixes #234

예제 3: Breaking Change

refactor: Change API response format

Changed the user API to return a more consistent response
structure across all endpoints.

BREAKING CHANGE: The /api/users endpoint now returns
{ data: [...], meta: {...} } instead of just [...]

유용한 표현들

  • Prevent - ~을 방지하다
  • Ensure - ~을 보장하다
  • Enable - ~을 가능하게 하다
  • Disable - ~을 비활성화하다
  • Allow - ~을 허용하다
  • Avoid - ~을 피하다

체크리스트

  1. 적절한 type을 사용했는가?
  2. 제목이 50자 이내인가?
  3. 명령형 동사를 사용했는가?
  4. 무엇을, 왜 변경했는지 명확한가?
  5. 관련 이슈 번호를 포함했는가?

정리

일관되고 명확한 커밋 메시지는 프로젝트의 히스토리를 이해하는 데 큰 도움이 됩니다. 처음에는 어색할 수 있지만, 규칙을 따라 작성하다 보면 자연스럽게 좋은 커밋 메시지를 작성할 수 있게 됩니다.
